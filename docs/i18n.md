# Localization

pyrlyn tools localize user-facing strings with [GNU gettext](https://www.gnu.org/software/gettext/)
catalogs: one `messages.pot` template and one `<lang>.po` per language.

gettext was chosen over [Fluent](https://projectfluent.org/). cox's Fluent groundwork
([pyrlyn/cox#69](https://github.com/pyrlyn/cox/pull/69)) was closed;
[pyrlyn/cox#71](https://github.com/pyrlyn/cox/pull/71) (open at the time of writing) is the
gettext version and the reference implementation:

- catalogs embedded in the binary and parsed in pure Rust (`polib`), so no libintl at runtime;
- locale negotiated from the POSIX environment and the OS, with a per-message fallback chain
  that ends in English;
- named `{name}` placeholders, since gettext has none of its own;
- native resources for the desktop apps (Apple `.strings`/`.stringsdict`, Windows `.resw`)
  generated from the same catalogs.

Rules:

- English is the source language and the fallback for every missing message
  ([languages](languages.md)).
- Only human-facing text is translated; machine output (JSON, agent output, log keys) stays
  English and stable ([CLI output](cli-ux.md)).
